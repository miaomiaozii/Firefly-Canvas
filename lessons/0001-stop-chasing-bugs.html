停止追着
bug 跑

你现在的痛苦，不一定说明 bug 特别多；它更说明发现、定位和防复发仍然依赖人的记忆与点击。

不需要你把所有 bug 一个一个指出来。你应该定义关键旅程和优先级；工程系统负责批量发现、稳定复现并阻止复发。

先分清两种工作

救火 你发现一次异常，我们修一次。它能恢复当下，却会随着功能和模型数量线性增长。
建设免疫系统 一次异常变成一个自动信号；以后任何改动触发同类错误，合并或发布立即被拦住。

Google SRE 把手工、重复、可自动化、没有持久价值、会随规模线性增长的工作称为 toil。让你不停点画布找 bug，正是这种工作。正确目标不是更勤快地找，而是让每次人工发现都减少未来的人工发现。

刚才 Banana 事故说明了什么

表面症状是“4K 参数不对”。真正的问题跨了四层：

层可能看起来正确必须证明的合同
界面显示 4K、两张输入图用户选择进入项目请求
任务路由日志仍写 4K选中同系列真实 4K 模型
适配器请求能成功返回最终请求仍有 image_size=4K
媒体边界显示“2 输入图”两张图片按顺序进入 multipart

所以一次 UI 手测永远不够。我们最终建立的是 5 个模型族 × 3 个分辨率的路由矩阵，再加最终假 HTTP 边界断言。这种测试不花 provider 费用，而且能准确指出坏在哪一层。

参数矩阵
秒级 模块合同

补盲区
  1. 参数矩阵：覆盖模型族、1K/2K/4K、比例、参考图数量、固定/自动选择。
  2. 模块合同：在最终 HTTP 边界断言真实字段，禁止“中间日志正确、出站参数丢失”。
  3. 关键旅程：只保留少量高价值浏览器流程，例如生成、LLM 引图、重载、历史、下载、并发。
  4. 发布门禁：静态检查、目标模块、浏览器烟测、全量测试按速度分层执行。

Google Testing Blog 强调，反馈循环要快、可靠、能隔离失败；不是端到端测试越多越好。Google SRE 也建议：老项目不要企图一次性给所有函数补测试，而要先排业务关键面，并把每个已报告 bug 变成回归用例。

你和系统各自负责什么

你负责 定义最重要的 5 到 10 条用户旅程；说明什么错误绝不能接受；对真实输出的审美和业务正确性做判断。
系统负责 自动枚举参数组合；验证请求合同；重放关键旅程；保存失败证据；阻止已知错误再次进入可试用版本。

接下来不是继续盲修

对当前项目，建议先暂停新增功能，做一次短期“稳定化冲刺”：

  1. 列出七个风险面：画布交互、项目持久化、媒体引用、模型能力、provider 协议、任务并发、历史与下载。
  2. 每个风险面选一条最值钱的用户旅程，先形成 7 条烟测，而不是穷举所有按钮。
  3. 把现有已知事故映射到最小测试层；重复或矛盾的合同先统一。
  4. 形成一个质量门命令；未通过时不继续堆功能。
  5. 再做一轮主动探索 QA，由代理系统性扫描，而不是等你偶然碰到。
