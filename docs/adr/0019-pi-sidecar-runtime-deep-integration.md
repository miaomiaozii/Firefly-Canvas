# pi 基座采用 Node sidecar 运行时（一步到位）+ 深度融合要求

2026-09-13 用户拍板 `docs/agent-pi-roadmap.md` §4 的两个前置决策，并给出 pi 基座的产品级要求。

## 决策

- **pi 运行时 = Node sidecar（独立进程），一步到位**：不做"浏览器内嵌先行、以后再换"的两段式。会话跨页面刷新/重启持久，支撑长时自主运行（P3 托管模式的前提）。代价是分发需含 Node 运行时，接受。
- **控制台形态 = 节点式**：Agent 节点可拖拽/缩放/复制，复制节点 = 新建独立会话（与 `0012-agent-is-a-separate-node.md` 一致）。
- **`app/core.py` 拆分并入 P2 一并执行**：不单独立项，随 pi 桥接层引入时对 `app/` 做结构化重组（请求模型、异常、multipart 解析器分家），一次回归。
- **Excel 收集导出的首要消费者是 pi**：`export_dir` 能力（issue #58，已闭环）之外，(a) 前端补目录输入（P1 打标收集任务内），(b) 导出能力暴露为 pi 工具，pi 可在会话中直接调用。
- **Topaz 模型显示名保持中文**（"Topaz图像放大"/"Topaz视频放大"，`data/api_providers.json:3840/3902`）：UI 中文优先，接受与其他英文显示名混排。

## 深度融合要求（pi 基座的设计约束）

1. **接口与扩展点先行**：为画布向 pi 暴露的每个能力设计稳定接口（工具注册、上下文读取、事件流），新能力以插拔方式加入，不硬编码进桥接层。
2. **兼顾兼容性**：迁移期间现有 plan-first Agent（#14，`api_project_library.py` 的 plan/execute 链路）继续可用；pi 工具层与旧链路共享同一服务端权限层（plan hash 确认、字段锁定、项目隔离）。
3. **可读性 / 便于修改 / 插拔**：桥接协议、会话存储、工具定义各自独立模块，任何一层可单独替换（换 pi 版本、换会话后端、加工具）而不牵动全局。
4. **pi 可读取应用报错日志**：pi 通过受控工具读取 FastAPI 结构化日志（级别/时间/模块过滤），这是 pi 自我诊断的前提；日志访问有范围限制（不暴露 key/凭证明文）。
5. **定期清理与画布修复**：pi 拥有维护类工具（清理孤儿资产/半成品任务、校验项目完整性、修复损坏文件入口的自动化版本），在 P3 托管模式下可周期性运行。
6. **北极星**：自适应、自迭代、自修复——P2 把"pi 看得见、摸得着、修得了"的地基打全，P3 给自主权，P4（自我修复画布 bug）不再是远期愿景而是既定路径。

## Consequences

- 分发包体积与复杂度上升：需打包 Node 运行时与 sidecar 启动/守护逻辑（Windows 优先，跟随现有分发渠道 `0009-independent-release-channel.md`）。
- sidecar 生命周期管理成为新的故障面：崩溃自愈、僵尸进程回收、与 FastAPI 主进程的版本一致性校验必须进入 P2 验收标准。
- 日志访问工具意味着应用日志必须保持结构化（print→logging 迁移（issue #99）是前置依赖，已完成）。
- `app/core.py` 的拆分时机绑定 P2：P2 开工前 core.py 保持现状（#100 后的单一 BaseModel 来源状态不回退）。
