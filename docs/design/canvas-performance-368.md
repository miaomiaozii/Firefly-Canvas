# #368：核心画布节点数与交互耗时

本次只测量，不修改渲染、输入或保存路径。测量代码基线为 `abfd139`；每档使用新建的合成画布，不读取或复制用户项目。

## 方法

- 在本机 Windows 上用真实 Tabbit 浏览器和 `tests/tabbit_e2e_evidence.py` 的隔离服务入口。仅用回环 31xx 端口，运行数据、项目库、临时目录和服务端 HOME 独立。服务跳过与本试验无关的启动迁移；使用实际画布路由、持久化与默认快照延迟。浏览器阻止非测试源的 HTTP(S) 请求。
- 54、300、1000 个同构空图片卡片，固定网格、无连线和媒体，固定视口 1366×900。每轮轮换档位顺序。每个样本是一个新项目和新标签页；关闭 HTTP 缓存。服务和浏览器进程不重启，所以不称为整个应用的冷启动。
- **打开**：导航开始至核心画布载入就绪、全部节点 DOM 就位后的第二个 `requestAnimationFrame`（rAF），不是首次任意像素出现的时间。使用 `focus_node` 进入同一个目标节点。
- **单次 render**：直接调用产品 `render()`，用 `performance.now()` 计同步执行，并另计调用开始至其后第二个 rAF；验证原节点 DOM 被替换。每次打开测 8 次，帧间隔开，后者包含等待帧调度。
- **拖动**：真实 Playwright 鼠标从节点标题栏拖动，约 1.1 s，目标间隔 16 ms；记录拖动中 rAF 次数、间隔和坐标更新量，核对目标节点 DOM 与世界坐标。这里的 FPS 是 rAF 回调率，不是屏幕实拍帧率；同时报告每试次的帧间隔 p90（最近秩），避免平均值掩盖卡顿。
- **输入**：实际向 `#promptInput` 键入 8 个字符，核对浮出的 DOM 文本；用 `keydown.timeStamp` 起计至 `input` 捕获事件及其后第二个 rAF。第二个指标是可见反馈的近似，包含帧等待；不包含硬件输入/显示延迟，也不是 IME 测试。
- **保存**：等待输入的自动保存结束，拖动后点击真实保存按钮。以该次 PATCH 的 request start 至 response end 计时，另记录 TTFB；检查提交确实含拖后坐标、HTTP 200、`saved=true` 及 UI 已保存，最后读取隔离快照校验 revision 与坐标。不把按钮前的输入/拖动或请求前的序列化计入 PATCH 往返。

## 限制与后续建议

- **先验证局部渲染。** 同步 `render()` 的区间在三档完全分离，且实测目标节点 DOM 每次都被替换。下一轮可用相同样本比较按节点增量更新前后的耗时，并校验未改节点的 DOM 和编辑焦点不丢失。本票不做优化。
- **不要把 Tabbit 的 rAF 数字当作桌面帧率。** 多次测得约一秒的帧间隔，1000 节点每次只采到 5–7 个 rAF 回调、5 个真实 pointermove；输入事件的处理延迟也和双帧反馈延迟相差很大。浏览器调度及输入驱动的影响未剥离。建议用前台窗口、固定显示刷新率和 CDP 时间线复测拖动与可见反馈。首次打开的区间重叠，不能据此宣称单调增长或给出节点阈值。
- **将保存拆成两段再决定方案。** 用相同的单节点 PATCH 分开测「服务端接受变更」和「快照落盘」，再评估通过 WebSocket 报告已落盘的可行性。不要把「已接受」等同于「已保存」。
- 合成样本不覆盖连线、正文长内容、媒体、IME、真实大项目或不同硬件。这些场景需要另测。
